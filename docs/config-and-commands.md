# 配置与命令

## 配置原则

- 默认值保守。
- 高风险功能可关闭。
- 玩家可见文字可改。
- 玩法倍率、概率、列表、文案这类服主常调内容优先配置化。
- 颜色是否配置化取决于插件定位；固定状态语义可以用代码默认值并在文档说明。
- 内部技术参数、临时排错参数、错误配置后风险较高的参数不默认暴露；需要暴露时写清适用场景和安全范围。
- 配置读入时做校验。
- 配置错误要输出明确原因。

## 常见字段

```json
{
  "DebugLogging": false,
  "NotificationMode": "chat"
}
```

## 配置文件分工

插件目录常见做法是把运行配置和说明配置分开：

```text
config.json
config说明.json
```

`config.json` 是插件运行时读取的文件，应保持严格 JSON，不写 `//` 注释，避免解析器不兼容。

`config说明.json` 是给服务器管理员看的必需说明文件。它应保留真实配置结构，只在字段旁边补用途、默认值、单位/范围、可选值和必要示例；如果需要，可在开头加一个简短的“插件信息”对象和一条重载方式。

`README.md` 适合在源码仓库中记录插件总览、安装、命令和排错入口，供开发者和维护者阅读。本地 `build/package/<Plugin>` 测试目录可以保留其副本；只有最终对外 ZIP 默认排除它。不要因为 ZIP 不需要而从源码树或测试目录删除。

只要说明文件里有 `//` 注释，它就不是严格 JSON。插件运行时不应该读取它。

这种分工有几个好处：

- 服务器管理员能直接看懂字段含义。
- 插件读取配置时不依赖 JSONC / 带注释 JSON 解析。
- 更新配置时可以对照说明文件，不容易填错。
- 中文服可以额外提供中文说明，英文服可以保留英文说明。

说明文件只需要写清楚：

- 每个字段的用途和默认值。
- 数值的单位、范围或倍率计算。
- 枚举可选值、列表填写格式和必要风险。

安装流程、固定安全规则、上服验证和其他通用注意事项写在源码仓库的 README、项目文档或 wiki，不在 `config说明.json` 里重复。

## 配置说明写法

好的配置说明文件不是只列字段，而是把真实配置复制成一份可参考的样板，让服务器管理员能按结构修改。

推荐内容标准：

```text
1. 保留一份接近真实 config.json 的配置结构
2. 每个字段右侧写一句必要短注释
3. 复杂字段只在相邻位置补一两行说明
4. 倍率、概率、时间这类数值只补单位、范围或必要计算示例
5. 可选添加简短插件信息和重载方式；默认在插件信息和配置项说明前各加一个简短分隔标题，用户明确说不要时才省略
```

示例格式：

```jsonc
{
  "插件信息": {
    "名称": "PluginName",
    "版本": "1.0",
    "运行配置": "config.json",
    "重载方式": "PluginName.Reload"
  },
  "Rules": [
    {
      "BlueprintPath": "Blueprint'/Game/.../...'", // 资源蓝图路径，必须完整
      "Name": "显示名称",                          // 只用于备注或日志
      "Enabled": true,                             // true=启用，false=禁用
      "Multiplier": 2.5,                           // 倍率，2.5=250%
      "DurationMinutes": 120                       // 持续时间，单位：分钟
    }
  ]
}
```

字段注释保持一句话；可以保留一个简短插件信息对象和一条重载方式。默认在插件信息和配置项说明前添加简短分隔标题，用户明确说不要时才省略；不要追加联系方式或长注意事项尾块。

面向服主的范围说明优先写“必须大于等于 0”“必须大于 0”，只有公式或代码示例才使用 `>= 0`、`> 0` 等数学符号。数值 `0` 有特殊含义时写清对象和结果，例如“0 表示关闭命令冷却”“0 表示该项不收费”“0 表示不限制数量”，不能为了简短只写“0 表示关闭”。

样式参考只改用户指定的部分。用户只要求参考插件信息时，不要顺带重构下方配置项。

## 字符串模式

模式字段建议转小写：

```text
chat
server
screen
```

未知模式回退到默认值。

## 数值字段

数值字段要限制范围：

- 半径最小值
- 概率 `0.0..1.0`
- 颜色 `0.0..1.0`
- 倍率必须大于 `0`
- 数量必须大于 `0`

## Permissions 与多 VIP 分级

功能需要按 Permissions/VIP 组提供不同价格、冷却、额度、奖励或保护时，优先使用包含 `Default` 普通档的统一结构化组规则数组，不再另设一套“非 VIP 默认值”，也不要随着需求增加不断叠加 `FreeGroups`、`DiscountGroups`、`CooldownGroups` 等独立字段。

组规则应满足：

- 开始设计前先读取目标服务器真实的 Permissions 组名和等级来源，不让服主重复描述数据库里已有的组体系，也不凭示例硬编码组数。
- 大多数服务器通常使用 `Default` 表示普通用户、`Admins` 表示管理员，并常见 `VIP1`、`VIP2`、`VIP3` 递增命名；默认配置和说明示例可以采用这些名称，但实际 VIP 数量及是否存在 `SVIP`、`SSVIP` 等扩展组仍以目标服务器数据为准。
- `Default` 直接作为统一数组中的普通用户档和价格兜底，不再增加 `Normal`、`NonVIP`、`Default: true` 或顶层普通用户价格。VIP 玩家即使同时命中 `Default`，也由最高有效 VIP 档覆盖。
- 每条规则保留真实匹配字段，例如 `Group`，并直接携带该档业务值。`Name` 只有确实需要对外显示别名时才添加，不能替代实际组名。
- 玩家可能同时拥有多个永久组、限时组或动态组；运行时优先调用 Permissions API，并取最高有效档，不能命中第一组就停止，也不能依赖 API 返回顺序。
- 等级顺序只保留一个权威来源：优先使用服务器已有等级数据；没有现成等级时，可以明确约定配置数组从低到高排列、最后命中的档位生效；只有没有其他确定顺序时才增加显式 `Priority`，避免重复配置已有等级。
- 空组名、重复组规则、无法确定等级关系和非法业务值在加载配置时直接拒绝，保留上一份有效配置。
- `Admins` 通常单独执行管理员绕过或管理员专属逻辑，不混入 VIP 价格等级。
- 使用资格与价格/权益分开判定：允许使用不等于免费，免费也不应自动改变访问范围。
- 当组服务不可用且继续执行可能造成误扣费、误发奖励或错误保护时，拒绝本次操作，不静默套用普通档或免费档。

## 命令设计

玩家输入的正式聊天命令必须使用 `AddChatCommand` 注册，并在卸载时使用 `RemoveChatCommand` 注销。不要用 `AddOnChatMessageCallback` 自行解析来代替正式命令注册：通用聊天回调即使返回 `true` 阻止了游戏默认广播，也不会把消息标记为正式命令，聊天桥或其他观察插件仍可能把它记录、转发或重新发送。

AsaApi 的正式命令匹配首个 token，命中后执行回调、设置 `command_executed=true`，并在调用游戏原始聊天广播前返回。命令回调本身不需要额外的“隐藏”参数。

命令别名支持热重载时，不要在当前聊天命令回调栈内立即移除或重新注册命令。命令检查会直接遍历命令容器，回调内修改可能导致迭代器失效；应延迟到下一 tick/timer 再同步别名。

推荐玩家命令：

```text
/plugin
/plugin <mode>
/plugin status
/plugin cancel
```

推荐管理员命令：

```text
/plugin reload
Plugin.Reload
```

RCON / 控制台重载可以减少重启服务器次数。

## 命令回执

如果怀疑聊天命令回调重入，可以延迟发送消息，并保存玩家弱引用。
这只是排查手段，不应作为所有插件的固定写法；如果当前接口已稳定，保持简单同步回执即可。

## 对用户解释配置时的中文规则


- 面向中文服主的插件，控制台/cmd日志、RCON回复和 Status 输出也应优先用中文业务含义；英文配置名可以保留，但不要让运行输出只剩英文键值。
和服主/用户沟通时，配置名、Status 字段、日志字段可以保留英文原名，但必须配中文含义。不要只回复 `CleanupScope=CurrentMapOnly`、`Clean=false` 这种英文键值；应写成 `CleanupScope=CurrentMapOnly`：清理范围=当前地图，或 `Clean=false`：该权限组完全免清。

如果用户表示看不懂英文参数，应优先使用中文业务描述，再把英文配置名放在括号里，方便后续定位配置文件。
