# 开发原则

ASA API 插件的核心目标不是“尽快写出能跑的代码”，而是“在服务器长时间运行、多插件共存、玩家真实操作下仍稳定可维护”。

## 设计优先级

1. 稳定性
2. 可排错性
3. 性能
4. 配置化
5. 玩家体验
6. 代码优雅

代码风格不能压过可验证性。看起来合适的函数，也要确认它的调用链、触发频率和实际效果。

## 基本工作方式

- 先读现有代码，再决定改法。
- 先确认 API / Hook 签名，再写代码。
- 一次只改一个关键变量，尤其是排查崩服或服务器无响应时。
- 先列出可用 API / Hook，再比较触发时机、频率、对象来源和验证成本。
- 如果 Hook 直接给出目标对象，通常先评估是否足够满足需求。
- 如果需要扫描、timer 或高频 Hook，说明业务必要性和范围限制。
- 玩家可见文字、玩法倍率、概率、冷却等运营常调参数优先配置化；颜色和内部技术参数按插件定位、风险和维护成本决定是否暴露。
- 涉及数据库、Web 后端、机器人或外部系统联动时，先看同类成熟插件和当前项目已有做法。不要默认把 ASA 插件做成 HTTP API 客户端；ArkShop / ICE 这类插件直接读写 MySQL、读取本地配置、调用现有插件命令都是常见落地方式。只有直接数据库/现有命令路径明确做不了，或项目明确要求服务化架构时，再引入 Web API 中转、新服务、新队列或新抽象。

## 不要留下历史包袱

当主方案变更后，要删除旧逻辑：

- 旧 Hook
- 旧配置字段
- 旧文档说明
- 旧测试用例
- 旧日志
- 旧兜底路径

废弃代码会增加排错成本，也可能在重载、卸载或版本迁移时继续影响运行。

## 本地与服务器验证边界

本地可以验证：

- 编译通过
- 单元测试通过
- 打包结构正确
- 配置能解析
- 纯逻辑函数正确

服务器才能验证：

- Hook 是否实际触发
- 字段写入是否游戏内生效
- 是否与其他插件冲突
- 是否无响应/断联
- UI/聊天显示是否符合预期

汇报时要区分这两类验证。
