# 开发流程

ASA API 插件开发应按“确认接口、隔离核心逻辑、最小接入服务器、可观测验证、可回滚发布”的顺序推进。

## 1. 明确插件边界

先写清楚插件要处理什么事件、影响什么对象、向谁反馈结果、失败时如何退出。

需求说明至少包含：

- 触发来源：聊天命令、RCON、控制台、timer、Hook、外部文件等。
- 目标对象：玩家、恐龙、建筑、库存、资源箱、世界 actor、服务器状态等。
- 状态生命周期：一次性、持续到重启、按时间过期、按事件清理。
- 配置项：开关、倍率、概率、冷却、权限、消息文本。
- 验证方式：日志、游戏内可见效果、测试用例、服务器侧观测项。

## 2. 确认 API 和 Hook

接口确认顺序：

1. ASA API Wiki / 官方文档。
2. ArkServerApi/AsaApi GitHub。
3. 当前项目已使用的源码。
4. 本地 `AsaApi` SDK（只在 Wiki 缺资料、疑似过期或编译/签名对不上时使用）。
5. 其他开源插件或论坛讨论。

只有官方文档 / Wiki，或必要时本地 SDK 能确认函数、字段、签名时，才能把它写成 API 事实。其他来源只能作为实现参考或待验证假设。

## 3. 设计代码分层

推荐把可测试逻辑放到 `core`，把 AsaApi 接入放到 `plugin`：

- `core`：配置解析、规则匹配、状态管理、文本模板、数值计算。
- `plugin`：命令注册、Hook 注册、游戏对象读取/写入、消息发送、日志。

这样可以让多数逻辑在普通测试程序里验证，减少每次都依赖真实服务器排错。

## 4. 编写接入层

接入层应保持短路径：

- 命令回调只做解析、权限、状态变更和回执。
- Hook 回调只处理当前事件需要的对象。
- Timer 有明确间隔、次数上限和退出条件。
- 日志能定位阶段，但不会在高频路径刷屏。
- 所有注册的命令、Hook、timer 在卸载或重载时能清理。

## 5. 配置和命令同步

新增行为时同步更新：

- 代码默认值。
- `config.json`。
- 配置说明文件。
- 源码仓库 README / 项目文档中的命令说明。
- 测试用例。
- 发布检查清单中的验证项。

不要只改代码不改配置，也不要保留已经不读取的旧字段。

## 6. 验证顺序

本地验证：

- Release 编译。
- core tests。
- 配置解析和默认值。
- 包目录结构。
- DLL 时间和 zip 时间。

服务器验证：

- 插件加载日志。
- 命令和权限。
- Hook 是否触发。
- 功能是否游戏内生效。
- 是否与其他插件共存。
- 长时间运行是否有 crash、无响应或异常日志。

## 7. 发布和回滚

每个测试包或正式包都应能回答：

- 版本号是什么。
- DLL 时间是什么。
- 配置是否有兼容变化。
- 本地验证做了什么。
- 服务器还需要测什么。
- 出问题回滚到哪个包。

正式发布前保留上一版可用 DLL 和配置，避免线上排错时没有回退路径。
