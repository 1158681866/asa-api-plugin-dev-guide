# 开发流程

ASA API 插件开发应按“确认接口、隔离核心逻辑、最小接入服务器、可观测验证、可回滚发布”的顺序推进。

## 1. 明确插件边界

先写清楚插件要处理什么事件、影响什么对象、向谁反馈结果、失败时如何退出。

需求说明至少包含：

- 触发来源：聊天命令、RCON、控制台、timer、Hook、外部文件等。
- 目标对象：玩家、恐龙、建筑、库存、资源箱、世界 actor、服务器状态等。
- 状态生命周期：一次性、持续到重启、按时间过期、按事件清理。
- 配置项：开关、倍率、概率、冷却、权限、消息文本。
- 验证方式：日志、游戏内可见效果、测试用例、服务器侧观测项。

## 2. 确认 API 和 Hook

接口确认顺序：

1. ASA API Wiki / 官方文档。
2. ArkServerApi/AsaApi GitHub。
3. 当前项目已使用的源码。
4. 本地 `AsaApi` SDK（只在 Wiki 缺资料、疑似过期或编译/签名对不上时使用）。
5. 其他开源插件或论坛讨论。

只有官方文档 / Wiki，或必要时本地 SDK 能确认函数、字段、签名时，才能把它写成 API 事实。其他来源只能作为实现参考或待验证假设。

## 3. 设计代码分层

推荐把可测试逻辑放到 `core`，把 AsaApi 接入放到 `plugin`：

- `core`：配置解析、规则匹配、状态管理、文本模板、数值计算。
- `plugin`：命令注册、Hook 注册、游戏对象读取/写入、消息发送、日志。

这样可以让多数逻辑在普通测试程序里验证，减少每次都依赖真实服务器排错。

## 4. 编写接入层

接入层应保持短路径：

- 命令回调只做解析、权限、状态变更和回执。
- Hook 回调只处理当前事件需要的对象。
- Timer 有明确间隔、次数上限和退出条件。
- 日志能定位阶段，但不会在高频路径刷屏。
- 所有注册的命令、Hook、timer 在卸载或重载时能清理。

## 5. 配置和命令同步

新增行为时同步更新：

- 代码默认值。
- `config.json`。
- 配置说明文件。
- 源码仓库 README / 项目文档中的命令说明。
- 测试用例。
- 发布检查清单中的验证项。

不要只改代码不改配置，也不要保留已经不读取的旧字段。

## 6. 验证顺序

本地验证：

- Release 编译。
- core tests。
- 配置解析和默认值。
- 本地 `build/package/<Plugin>` 测试目录结构及其本地配置。
- 最终对外 ZIP 条目白名单。
- DLL 时间和 zip 时间。

服务器验证：

- 插件加载日志。
- 命令和权限。
- Hook 是否触发。
- 功能是否游戏内生效。
- 是否与其他插件共存。
- 长时间运行是否有 crash、无响应或异常日志。

### 四类轻量检查

- **API 更新兼容检查**：仅在项目使用的 API / SDK 基线变化时执行。按权威 Skill 的 [SDK 更新判断](../skills/asa-api-plugin-dev/references/api-lookup.md#sdk-更新判断) 同时检查正式发布、稳定分支和本地 commit；区分头文件修正与核心/公开 ABI 变化，确认库来源并校准 `MinApiVersion`。完成 Release 全量重建、加载、核心功能、卸载和重新加载；出现 offset、签名或运行异常后再扩大审计范围。
- **未发布分支前向检查**：官方仓库中尚未合并、未发布的分支不能直接替换生产基线，但可以固定 commit 后，与正式 Release 比较当前插件实际使用的 Hook、`NativeCall`、字段 key 和公开接口；必要时做一次不发布产物的语法编译。门禁通过只说明依赖未被删除或改签名，不证明 offset、对象布局、Hook 链或运行行为兼容。分支若修改 AsaApi 核心、公开虚表或 Hook/offset 管理，必须用同源 headers、`AsaApi.lib` 和服务器 runtime 整体在隔离环境验证，不能与正式 Release 混搭。
- **危险代码审计**：使用当前环境可用的仓库搜索能力检查插件中的生命周期、裸游戏对象指针、危险存档接口、`NativeCall`、线程访问 UObject 和可重入 timer 等入口；有 `rg` 时优先使用，没有时采用等价工具。再结合上下文判断，关键字命中只是线索，不自动等于缺陷。
- **编译、测试和打包验证**：沿用当前插件已有工程、测试和打包脚本，不要求统一构建系统，也不要求指南仓库额外维护可编译模板插件。
- **规则一致性检查**：更新指南后搜索 `SKILL.md`、平台适配器、`references` 和 `docs` 中的旧写法或反向结论；权威源位于 Git 仓库时执行 `git diff --check`。随后安全同步各 Agent 客户端的部署副本，本地已有改动时不得整目录覆盖。

这些检查属于开发流程，不是插件运行功能。只有重复步骤长期稳定且人工容易漏检时，才提取成小型辅助脚本。

## 7. 发布和回滚

每个测试包或正式包都应能回答：

- 版本号是什么。
- DLL 时间是什么。
- 配置是否有兼容变化。
- 本地验证做了什么。
- 服务器还需要测什么。
- 出问题回滚到哪个包。

正式发布前保留上一版可用 DLL 和配置，避免线上排错时没有回退路径。
