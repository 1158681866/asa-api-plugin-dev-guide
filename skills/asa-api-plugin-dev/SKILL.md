# ASA API 插件开发

用于 Ark Survival Ascended 的 AsaApi C++ 插件开发。保持通用，不假设固定工作区、插件名、SDK 目录、服务器机器或个人路径。

## 开始前

1. 先从当前项目、工程文件、include 路径、打包脚本或任务说明里确认插件根目录和本地 AsaApi SDK 路径。
2. 改代码前先读现有实现。搜索符号、Hook、配置字段、崩溃关键字、旧逻辑时优先用 `rg`。
3. 每个引擎/API 符号先按当前项目使用的本地 AsaApi SDK 确认；wiki 用于检索和交叉确认：`https://arkserverapi.wiki/asa/index.html`。
4. 不确定的 Hook 签名、字段名、调用链必须标记为“待确认”，不要写成确定结论。
5. 行为改动要同步更新代码、默认配置、测试、包内文件和文档。
6. 完成后编译、跑已有测试、打包，并报告产物路径和 DLL 时间。
7. 区分 API 事实、社区常见结构和工程判断；不要把项目特定问题写成通用规则。
8. ASA 插件开发、排错或发布结束前，必须执行一次“自我迭代检查”：如果本轮暴露了可复用于多类 ASA 插件的坑点、验证步骤或稳定写法，应更新本 skill 或对应参考；如果只属于单个项目，应记录到项目文档。

## 工程判断

- 大范围扫描、高频全局 Hook、脚本派发、状态同步、setter 等做法需要说明业务必要性、触发频率、范围限制、可观测日志和回滚方式。
- 不靠猜测确定游戏对象路径、Outer 链、脚本派发、状态同步、setter 等调用链；不确定时先查 SDK、wiki 或现有项目代码。
- 会触发蓝图、脚本、网络同步或其他插件链路的调用要写清楚验证方式。
- 主方案变更后，不保留无用兜底系统、旧 Hook、废弃配置字段。
- 服务器不在本机时，不要声称“已上服验证”。只能说明本地编译/测试/打包已通过，并告诉用户服务器上要看哪些日志或效果。
- Debug 日志要有目标。发布前删除或用配置开关控制噪声日志。

## 常用流程

1. 阅读插件结构：源码、核心配置、测试、文档、打包脚本。
2. 在本地头文件或 wiki 中确认相关 API 符号。
3. 做范围清晰、可验证、可回滚的代码/配置/文档/测试改动。
4. 编译 Release。优先使用项目现有构建方式；Windows 常见方式是 MSBuild，参数为 `Configuration=Release`、`Platform=x64`。
5. 运行已有单元测试或 core tests。
6. 如果有打包脚本，执行打包脚本。
7. 检查包目录里是否有 DLL、`PluginInfo.json`、`config.json`、`config说明.json`。`README.md` 可选。
8. 执行自我迭代检查：判断本轮经验是通用 skill、项目文档、还是无需记录。
9. 交付时说明改了什么、怎么验证、包目录、DLL 时间，以及服务器上还需要测试什么。

## 发布包文档标准

- `PluginInfo.json`：保持原标准，仍然必需。
- `config.json`：保持严格 JSON。
- `config说明.json`：必需的中文配置说明文件。
- `README.md`：可选，保留给项目自己的总览和安装说明。

## 设计倾向

选型时先说明业务目标、可用 API、调用频率、目标对象来源和验证方式。事件 Hook、短时重试、字段写入、timer、全局 Hook 都只是工具；是否合适取决于插件目标和实测结果。

配置设计要区分两类内容：

- 服务器管理员经常会改、且影响玩法或文案的内容，优先配置化。
- 只服务内部实现、排错阶段、或错误配置会明显增加风险的技术参数，不默认暴露给配置；需要暴露时写清适用场景和安全范围。

## 自我迭代

当一次开发或排错产生可复用经验时，必须在结束前主动判断它是否覆盖多类 ASA API 插件、服务器环境或问题类型。只有具备通用价值的内容才沉淀到本 skill 或指南；单个项目、单次兼容问题、私有路径、聊天话术、经济数值、奖励表等不要写入通用技能。

如果经验来自单个案例，把它抽象成风险评估问题、验证步骤或适用条件；不要直接写成绝对禁令或 API 事实。更新时优先记录到该项目自己的维护文档或变更记录。

如果判断结果是“应该更新 skill”，不要只在最终回复里建议；应直接修改对应 `SKILL.md` 或 `references/*.md`，再在最终回复中说明已更新。只有在缺少权限、路径不可写或规则边界不清时，才说明未自动更新的原因。
