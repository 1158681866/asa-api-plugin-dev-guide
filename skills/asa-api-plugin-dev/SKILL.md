# ASA API 插件开发

用于 Ark Survival Ascended 的 AsaApi C++ 插件开发。保持通用，不假设固定工作区、插件名、SDK 目录、服务器机器或个人路径。

## 最高原则

不管实现什么功能，默认第一依据是 ASA API 官方文档 / Wiki；文档里有明确 API、签名或推荐写法时，按文档实现。文档不足、疑似过期或编译对不上时，再查当前项目使用的本地 AsaApi SDK 头文件确认；最后才参考成熟插件源码。只有官方文档、标准封装、SDK helper 和公开安全函数都没有覆盖，且业务必须、风险已隔离时，才考虑底层字段、组件字段、私有类信息、`NativeCall` 或手写偏移。

## 开始前

1. 先从当前项目、工程文件、打包脚本或任务说明里确认插件根目录；不要把本地 AsaApi SDK 当默认查询来源。
2. 改代码前先读现有实现。搜索符号、Hook、配置字段、崩溃关键字、旧逻辑时优先用 `rg`。
3. 每个引擎/API 符号和功能入口优先查官方文档 / ASA API wiki：`https://arkserverapi.wiki/asa/index.html`；Wiki 足够时直接按文档做并停止，不为了“保险”先翻 SDK 或成熟插件源码。只有官方没有、写得不清楚、疑似过期，或已经出现编译/签名不一致时，才用本地 AsaApi SDK 做最后确认。`文档优先` 高于 `SDK 里字段能编译`。
4. 访问游戏对象时先从 API 文档/wiki 查 AsaApi/ArkApi 标准封装、官方推荐接口、`AsaApi::GetApiUtils()`、SDK helper 或对象公开安全函数；不要一开始就直接碰底层字段、组件字段、私有类信息、`GetNativePointerField`、`NativeCall` 或手写偏移。只有确认没有标准封装、业务必须、并已把风险集中隔离时才使用底层访问。
5. 不确定的 Hook 签名、字段名、调用链必须标记为“待确认”，不要写成确定结论。
6. 行为改动要同步更新代码、默认配置、测试、包内文件和文档。
7. 完成后编译、跑已有测试、打包，并报告产物路径和 DLL 时间。
8. 区分 API 事实、社区常见结构和工程判断；不要把项目特定问题写成通用规则。
9. ASA 插件开发、排错或发布结束前，必须执行一次“自我迭代检查”：如果本轮暴露了可复用于多类 ASA 插件的坑点、验证步骤或稳定写法，默认自动更新本 skill 或对应参考，不等待用户提醒；如果只属于单个项目，应记录到项目文档；只有是否适合通用化存在明显争议、可能误导他人、或需要包含项目私有内容时，才先向用户确认。


## 用户沟通与配置解释

- 面向服主或用户解释配置项、Status 输出、日志字段、数据库字段、命令参数时，不要只写英文参数名或枚举值。必须同时给出中文含义，格式优先采用：`英文参数`：中文解释。
- 当回复里出现 `CleanupScope=CurrentMapOnly`、`CrossMapActiveProtection=true`、`PermissionRules`、`Clean=false`、`InactiveDays=90` 这类字段时，必须紧跟中文说明，例如“清理范围=当前地图”“跨地图活跃保护=开启”“权限组/VIP 分级规则”“该组完全免清”“90 天不活跃才清理”。
- 如果用户已经明确表示看不懂英文参数，后续同一任务中应优先用中文业务表述，再把英文参数作为括号里的配置名或排查线索。
- README、`config说明.json`、Status 输出可以保留必要英文配置名；但对话总结、方案解释和交付说明必须带中文解释，不能假设用户会读配置说明文件。
- 如果插件面向中文服主或用户已要求中文，插件自己的控制台/cmd日志、RCON回复、Status输出也应优先用中文业务含义；必要英文配置名只作为定位线索保留，例如“试运行=开启”“数据库可用=可用”“清理范围=当前地图”。

## 工程判断

- 玩家输入的正式聊天命令必须优先使用 `AddChatCommand` / `RemoveChatCommand` 注册与注销，不得用 `AddOnChatMessageCallback` 手工解析来代替。正式命令命中后应由 AsaApi 阻止原消息广播，并让其他聊天观察插件收到 `command_executed=true`；通用聊天回调只用于普通聊天的观察、过滤或修改。动态重载命令别名时，不要在当前聊天命令回调栈内直接删改命令容器，应延迟到下一 tick/timer。
- 大范围扫描、高频全局 Hook、脚本派发、状态同步、setter 等做法需要说明业务必要性、触发频率、范围限制、可观测日志和回滚方式。
- 定时器任务如果也能被 RCON/控制台手动触发，必须考虑重入/并发执行。对会遍历全图、写审计表、Destroy Actor、发奖励、改权限或改数据库状态的任务，稳定写法是在任务入口加互斥/运行中标记，并在 Status 或日志里暴露 running/skipped 状态，避免重复执行导致重复清理、重复发放或任务状态混乱。
- 不靠猜测确定游戏对象路径、Outer 链、脚本派发、状态同步、setter 等调用链；不确定时先查官方文档 / wiki。Wiki 够用就停止，只有缺资料或编译对不上才查 SDK。
- 对象路径、玩家位置/朝向、玩家 ID、部落 ID、聊天/通知、蓝图路径、世界对象、Actor/Structure 范围扫描、物品蓝图、权限判断等常见能力，先查 `AsaApi::GetApiUtils()`、SDK helper、官方文档或对象公开安全函数。不要因为底层字段“能编译”就直接使用。
- 需要按部落 ID 获取建筑、恐龙、角色等 Actor 时，不要默认先 `GetAllActorsOfClass` 后逐个读取 `TargetingTeam` 过滤；当前官方 SDK 头文件可能提供 `UGameplayStatics::GetAllActorsOfClassInTribe(...)`。应先确认当前 Wiki/SDK 的签名和当前 API 版本能否解析该 `NativeCall`，再做最小上服基准测试。函数名只能证明它提供“按部落返回结果”的入口，不能仅凭命名断言其内部一定维护了高性能索引；是否减少扫描开销要以实测或逆向结果为准。
- 对大型 Actor 队列按位置、高度、血量或其他 UObject 字段排序时，不要在 `std::sort` / `std::stable_sort` 比较器里反复执行 `weak.Get()`、`GetLocation()`、字段访问或 `NativeCall`。先线性遍历一次，把每个 Actor 的排序键缓存到临时记录，再让比较器只比较数字/字符串等普通值；这样把昂贵的游戏对象访问从 `O(N log N)` 降为 `O(N)`，同时继续用弱引用并在真正处理前复核有效性。
- 如果必须用底层字段、组件字段、私有类信息、`NativeCall` 或手写偏移，必须满足：没有可用标准封装；访问集中在小函数内；有空指针/异常保护；有注释说明“未找到更高层封装/待上服验证”；高风险写字段路径必须放在明确配置开关或管理员命令后面。
- 会触发蓝图、脚本、网络同步或其他插件链路的调用要写清楚验证方式。
- 清理建筑、容器、库存类 Actor 时，要考虑删除动作可能在后续 Tick 生成 `ADroppedItem`、死亡包、库存包等二级 Actor；地基/支撑先被删除时，上面的工作台、保险柜、箱子等容器还可能由游戏后续判定“失去支撑”再炸掉，并生成新的库存缓存包。若业务目标是“清干净资产”，应在主对象删除后留出短延迟，至少做一次掉落物/缓存类扫描；对支撑链导致的容器缓存，建议再复查一次同部落结构/容器类 Actor，然后再做最终掉落物扫描。为了避免误清，优先按明确归属字段（例如 `ADroppedItem.AssignedToTribeID`、结构 `TargetingTeam`）判断；不要仅凭距离、名称或模糊猜测清理其他玩家可能拥有的包裹。
- 大批量 Actor 清理如果拆到多个 Tick 执行，不要在队列中长期保存裸 `AActor*` 指针；ASA/UE 可能在支撑链、Destroy、GC、Mod 蓝图或其他插件逻辑中让队列里尚未处理的对象提前失效。稳定写法是按 ASA API Wiki 暴露的 `GetWeakReference(actor)` 保存 `TWeakObjectPtr<AActor>`，处理前再 `weak.Get()` 取有效对象；或保存可重新解析的标识并每批处理前重新扫描、重新校验归属。不要猜 `TWeakObjectPtr<AActor>(actor)` 这种构造写法；每次访问 `TargetingTeamField()`、位置、`Destroy()` 前都要重新取有效对象并兜底跳过无效对象。
- 不要为了日志展示、状态文本、队列预览这类非核心功能，在定时器/扫描/清理链路里调用会加载或复制存档级数据的接口，例如 `AShooterGameMode::GetOrLoadTribeData()` / `LoadTribeData()`。ASA 某些版本在服务器刚启动、定时器早期或数据未稳定时可能在 `FTribeData::CopyFrom()` / `TArray<FString>::operator=()` 崩溃；展示字段读不到时应使用“暂未读到”等兜底，或只使用已经在线/已加载对象上现成的安全字段。
- 主方案变更后，不保留无用兜底系统、旧 Hook、废弃配置字段。
- 服务器不在本机时，不要声称“已上服验证”。只能说明本地编译/测试/打包已通过，并告诉用户服务器上要看哪些日志或效果。
- Debug 日志要有目标。发布前删除或用配置开关控制噪声日志。
- 自动运行/定时维护类插件的正式运行日志不能只在“有处理对象”时写；插件启动、配置加载、数据库初始化、定时器启动、任务跳过、无候选/无动作扫描、异常和卸载都应有低噪声文件日志，方便确认插件确实在运行。

## 常用流程

1. 阅读插件结构：源码、核心配置、测试、文档、打包脚本。
2. 优先在官方文档 / wiki 中确认相关 API 符号；足够时停在这里。不足或编译对不上时，再查本地头文件和成熟插件源码。
3. 做范围清晰、可验证、可回滚的代码/配置/文档/测试改动。
4. 编译 Release。优先使用项目现有构建方式；Windows 常见方式是 MSBuild，参数为 `Configuration=Release`、`Platform=x64`。
5. 运行已有单元测试或 core tests。
6. 如果有打包脚本，执行打包脚本。
7. 检查包目录里是否有 DLL、`PluginInfo.json`、`config.json`、`config说明.json`。`README.md` 可选。
8. 执行自我迭代检查：判断本轮经验是通用 skill、项目文档、还是无需记录；凡是通用且边界清晰的内容应直接补到 skill/指南，不把判断工作留给用户。
9. 交付时说明改了什么、怎么验证、包目录、DLL 时间，以及服务器上还需要测试什么。

## 发布包文档标准

- `PluginInfo.json`：保持原标准，仍然必需。
- `PluginInfo.json` 必须使用 AsaApi 期望的数字字段：`Version` 和 `MinApiVersion` 都写 JSON number，不要写 `"0.1.0"` 这类字符串，也不要漏写 `MinApiVersion`。
- `config.json`：保持严格 JSON。
- `config说明.json`：必需的中文配置说明文件。格式可按项目需要选择“字段表式结构”或“JSONC 短注释样例”；面向小白服主时优先用类似 ArkShop 的紧凑 JSONC 排版，把解释放在配置项同一行或相邻短注释里。只覆盖公开配置项的必要中文含义、默认值/常用值、单位、可选值和风险开关；不要另加顶部声明、通用命令、固定安全规则、上服验证或底部注意事项块，这些内容放在 `README.md` 或项目文档。
- 说明文案使用正式、简明的运维语气：每项保留用途、单位/范围、默认或案例值和关键行为；不要过度简化成“开/关”说明，也不要写成长篇教程。JSONC 注释不重复 `Database.Host` 这类完整英文路径，配置层级本身已表达位置。
- `README.md`：可选，保留给项目自己的总览和安装说明。
- 对外发布的 ZIP/压缩包不得包含真实数据库名、用户名、密码、Token 或服务器专用凭据。如果本地 `build/package/<Plugin>` 文件夹同时是实际上服目录、必须保留真实配置，不要为了发布去覆盖它；应复制到临时 ZIP staging 目录，只在临时副本中替换为明确占位符，对该副本重新执行配置和敏感信息校验后再压缩，并在验证脚本中同时断言“ZIP 已脱敏”和“本地发布文件夹未变化”。
- `YOUR_*` 一类占位符只用于必须脱敏的凭据，例如数据库名、用户名、密码、Token、密钥或服务器专用地址；普通玩法和权限配置应保留可读的案例值，例如 `VIP1`、`Admin`、常规数值和枚举值。
- 公开 `config.json` 不得为了演示格式而预填会实际生效的假数据，例如白名单/黑名单 ID、奖励对象、Webhook 地址或权限名单；此类字段应保持安全默认值（空数组、关闭或无目标）。需要展示填写格式时，在 `config说明.json` 的 JSONC 示例中分行标注示例值和“示例”注释。
- 发布验证除检查凭据未泄漏外，还应断言 ZIP 内的公开配置与预期安全模板一致，且本地部署文件夹仍保留原配置。
- 公开压缩包展示名与包内插件标识分离。采用固定中文展示名的项目，正式包使用 `<中文插件名>.zip`，不在文件名重复版本号或作者；版本以 `PluginInfo.Version` 为准，ZIP/DLL SHA256、生成时间和验证结果记录在包外发布记录或交付说明中。
- `PluginInfo.FullName` 保持稳定的英文内部标识；面向服主的加载说明使用字段分隔格式：`<展示名> · <核心功能> · 作者：<署名>[ · QQ：<公开号码>]`。AsaApi 已自动输出 `FullName` 与 `Version`，说明文字不要再次重复版本号；联系方式默认不写入，只有作者明确要求公开时才追加 QQ。发布前必须确认 QQ 不与本机凭据、Token 等敏感值冲突；若冲突，应改用其他联系方式或先更换真实凭据，不能为保留联系方式而放宽泄漏检查。

## 设计倾向

选型时先说明业务目标、可用 API、调用频率、目标对象来源和验证方式。事件 Hook、短时重试、字段写入、timer、全局 Hook 都只是工具；是否合适取决于插件目标和实测结果。

涉及数据库、Web 后端、机器人或外部系统联动时，先参考同类成熟 ASA 插件和当前项目已有做法，再设计通信链路。不要默认把 ASA 插件做成 HTTP API 客户端；ArkShop / ICE 这类插件直接读写 MySQL、读取本地 config、调用现有插件命令都是常见落地方式。只有在直接数据库/现有命令路径明确做不了、或用户要求服务化架构时，再引入 Web API 中转、新服务、新队列或新抽象。

配置设计要区分两类内容：

- 服务器管理员经常会改、且影响玩法或文案的内容，优先配置化。
- 只服务内部实现、排错阶段、或错误配置会明显增加风险的技术参数，不默认暴露给配置；需要暴露时写清适用场景和安全范围。

## 自我迭代

当一次开发或排错产生可复用经验时，必须在结束前主动判断它是否覆盖多类 ASA API 插件、服务器环境或问题类型。只有具备通用价值的内容才沉淀到本 skill 或指南；单个项目、单次兼容问题、私有路径、聊天话术、经济数值、奖励表等不要写入通用技能。

如果经验来自单个案例，把它抽象成风险评估问题、验证步骤或适用条件；不要直接写成绝对禁令或 API 事实。更新时优先记录到该项目自己的维护文档或变更记录。

如果判断结果是“应该更新 skill”，不要只在最终回复里建议，也不要等用户追问；应直接修改对应 `SKILL.md` 或 `references/*.md`，再在最终回复中说明已更新。只有在缺少权限、路径不可写、规则边界不清、或内容可能把单个项目经验误写成通用规则时，才说明未自动更新的原因并请求确认。

## 数据库依赖注意

- ASA 插件如果直接包含旧版 MySQL C Connector 头文件（例如 ArkShop/Permissions 附带的 `mysql/mysql.h`），在 Windows/AsaApi 工程里可能因为 `WIN32_LEAN_AND_MEAN` 导致 `SOCKET/my_socket` 未定义。稳定写法是在包含 MySQL 头前先包含 `winsock2.h`，并确保链接 `Ws2_32.lib`；不要只靠 `Windows.h` 间接带出 socket 类型。
- 写入 MySQL `VARCHAR`/`TEXT` 字段前，尤其是玩家名、中文日志、路径、RCON 文本、审计 reason/note，要按目标字段长度做 UTF-8 安全截断，不要直接 `std::string::substr()` 截固定字节。直接按字节截断可能切断多字节字符，在 `utf8mb4` + 严格模式下导致 INSERT/UPDATE 失败，进而让任务状态、审计表或活跃表停在中间态。
- 数据库型 ASA 插件发布前，README 或运维文档里应给出可直接复制的自检 SQL/命令，至少覆盖：核心表是否创建、最近写入记录、任务/审计状态分布、失败记录计数、关键安全字段或跳过原因。发布包验证脚本也应检查这些自检入口是否存在，避免代码功能完整但上服后缺少可操作验收路径。
