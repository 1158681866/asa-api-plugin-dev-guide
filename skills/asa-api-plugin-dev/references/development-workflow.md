# 开发流程

用于新建插件、重构主链路或补齐发布流程时。

## 工作顺序

1. 明确触发来源、目标对象、状态生命周期、配置项和验证方式。
2. 按 ASA API Wiki / 官方文档优先确认接口；Wiki 足够时不查 SDK。
3. 把可测试逻辑放在 `core`，把 AsaApi Hook、命令、游戏对象访问放在 `plugin`。
4. 接入层保持短路径：解析、权限、目标对象、状态变更、回执或日志。
5. 同步更新代码默认值、`config.json`、配置说明、源码仓库 README / 项目文档、测试、本地测试目录和最终对外 ZIP；README 的权威版本保留在源码树，本地 `build/package/<Plugin>` 可以保留副本，只有最终 ZIP 默认排除它。
6. 先本地编译和测试，再做服务器验证。
7. 发布时记录版本、DLL 时间、配置变化、验证结果和回滚包。

## 判断边界

- 本地能验证编译、纯逻辑测试、配置解析和包结构。
- 服务器才能验证 Hook 触发、游戏内效果、多插件兼容和长时间稳定性。
- 无法从 SDK、wiki 或可复现实测确认的内容，不写成 API 事实。

## 四类检查如何落地

1. **API 更新兼容检查**只在项目使用的 API / SDK 基线变化时执行。先按 [SDK 更新判断](api-lookup.md#sdk-更新判断) 同时比较正式发布、稳定分支和本地 commit，区分纯头文件修正与核心/公开 ABI 变更，确认导入库来源和兼容依据，并校准 `MinApiVersion`。完成 Release 全量重建、加载、核心功能、卸载和重新加载；出现 offset、签名或运行异常后再深入检查缓存和具体接口。
   官方仓库中尚未合并、未发布的开发分支不应直接替换生产基线，但可以作为前向兼容门禁：固定分支 commit，把当前插件实际使用的 Hook key、`NativeCall` key、字段 key 和公开接口与正式 Release 做集合差分，必要时增加一次不发布产物的语法编译。通过这类检查只代表“当前依赖没有被该分支删除或改签名”，不能证明运行时 offset、对象布局、Hook 链和服务器行为已经兼容。开发分支若修改 AsaApi 核心、公开虚表或 Hook/offset 管理，必须使用同源 headers、`AsaApi.lib` 和服务器 runtime 整体隔离验证；不得把开发分支头文件与正式 Release 的库或 `AsaApi.dll` 混搭。
2. **危险代码审计**以当前插件源码为范围。先用当前环境可用的仓库搜索能力检查生命周期、命令 `Remove*`、`GetOrLoadTribeData`、跨 Tick 裸 `AActor*`、`NativeCall`、线程访问 UObject、可重入 timer 等入口；有 `rg` 时优先使用，没有时采用等价工具。再阅读上下文确认是否真的存在风险。不要把关键字命中直接当成错误，也不要为了偶发检查建立大型通用扫描系统。
3. **编译、测试和打包验证**使用项目已有 `.sln/.vcxproj`、测试程序和 `package.ps1`。没有现成测试时按本次改动补最小可验证项，不要求指南仓库提供一个额外可编译插件。
4. **规则一致性检查**用于维护指南本身。更新规则后搜索 `SKILL.md`、平台适配器、`references` 和 `docs` 中的旧写法或反向结论；权威源位于 Git 仓库时执行 `git diff --check`。最后把变更安全同步到需要使用它的 Agent 客户端，部署副本有本地改动时不得整目录覆盖。

这四项是开发流程门禁，不是插件运行功能。只有重复操作已经稳定、人工执行经常遗漏时，才把对应步骤提取成小型辅助脚本。
