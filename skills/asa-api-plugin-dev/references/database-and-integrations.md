# 数据库与外部系统

仅在插件直接使用 MySQL、共享任务表、机器人、Web 后端或其他进程间通信时读取。

## 先选最窄集成边界

- 先检查当前项目和成熟同类插件已经使用的 MySQL 表、插件命令、本地配置或公开 API。不要默认把 ASA 插件做成新的 HTTP 客户端、Web 服务或消息队列消费者。
- 只有直接数据库、现有命令或既有协议明确无法满足需求，或用户明确要求服务化架构时，才新增 Web API、sidecar、队列或跨进程抽象。
- 定义外部契约时，把字段、鉴权、幂等键、状态机、错误码、超时、重试和版本兼容写清；连接成功、心跳或 HTTP 200 不等于业务副作用已经完成。

## Windows MySQL 构建与字符串

- 直接包含旧版 MySQL C Connector 头文件（例如 `mysql/mysql.h`）时，`WIN32_LEAN_AND_MEAN` 可能导致 `SOCKET` / `my_socket` 未定义。稳定写法是在 MySQL 头之前包含 `winsock2.h`，并链接 `Ws2_32.lib`；不要只依赖 `Windows.h` 间接声明 socket 类型。
- 写入 MySQL `VARCHAR` / `TEXT` 前，尤其是玩家名、中文日志、路径、RCON 文本、审计 `reason/note`，按目标字段长度做 UTF-8 安全截断。不要直接用固定字节 `std::string::substr()`，否则可能截断多字节字符并在 `utf8mb4` 严格模式下让 INSERT/UPDATE 失败。

## 多进程任务领取与副作用

- 多服或多插件进程消费同一任务表时，不能“先 SELECT pending，再执行奖励，最后 UPDATE”。在任何外部副作用前，用带状态和归属条件的单条 `UPDATE pending -> processing` 原子 claim；只有 affected rows 恰好为 1 才继续。
- 完成、失败恢复和 stale 回收都要同时校验 `status`、`executor`、`server_key/owner`，避免其他进程接管后仍回写旧任务。
- 发背包物品、执行控制台命令等游戏副作用不能与 MySQL 事务原子提交。至少区分“已 claim、尚未开始副作用”和“副作用已开始”：前者确认无结果时可恢复 `pending`；后者遇到崩溃、部分成功或数据库确认失败时进入人工核对状态，不自动重试造成重复发放。
- stale processing 回收按副作用阶段分别处理，并记录 claim、开始副作用、结果确认和隔离原因。不要仅靠时间超限统一重置为 pending。

## 网络线程与游戏线程

- WebSocket、HTTP、Named Pipe 或其他网络线程只处理协议、鉴权、心跳和有界纯数据队列；不得访问 `UWorld`、玩家控制器、背包或其他 UObject。
- 入站通知回到 ASA timer/游戏线程后，重新查询权威数据库或当前配置，再执行游戏对象操作。不要把网络事件携带的旧对象指针或旧权限判断直接用于副作用。
- 卸载先停止接单，关闭可取消的阻塞句柄，停止并 join 网络线程，再释放数据库连接、队列和插件全局状态。

## 发布与运维自检

- 数据库型插件的源码 README 或运维文档提供可复制的自检 SQL/命令，至少覆盖：核心表是否创建、最近写入、任务/审计状态分布、失败记录计数、关键跳过原因或安全字段。
- 发布验证检查这些运维入口存在且与当前 schema 一致，但不因此把 README 强行放进公开 ZIP。
