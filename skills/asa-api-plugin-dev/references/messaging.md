# 聊天与通知

根据想要的游戏内样式选择消息接口。

## 常见接口

- `SendChatMessage(player, sender_name, msg)`：普通聊天行，有发送者名，通常没有单独颜色参数；如果需要简单颜色，可评估消息正文是否支持游戏富文本标签。
- `SendServerMessage(player, color, msg)`：服务器/直发聊天样式，有颜色，发送者通常偏服务器消息。
- `SendNotification(player, color, scale, time, icon, msg)`：屏幕通知，不是聊天框历史里的普通消息行。
- `ClientServerChatDirectMessage(&message, color, bold, &sender)`：直发聊天行，有发送者名，也有颜色；实际显示样式可能接近服务器直发消息，需要在目标服务器里截图确认。

所有接口优先按官方文档 / ASA API Wiki 核对签名；Wiki 足够时不查 SDK。只有 Wiki 缺资料、疑似过期或编译/签名对不上时，再用本地 SDK 补充确认。

## 实用选择

- 想要普通“发送者：内容”聊天行：优先评估 `SendChatMessage`。
- 想要普通聊天行且需要颜色：先验证正文富文本标签是否满足需求，再考虑直发接口。
- 想要有颜色的直发/服务器样式消息：评估 `SendServerMessage` 或 `ClientServerChatDirectMessage`。
- 想要屏幕上方/中间的浮动提示：用 `SendNotification`。

`SendChatMessage` / `SendChatMessageToAll` 能构造带自定义发送者名称的聊天行，但这不等于一名真实登录玩家发出的服务端聊天。发送者 ID、平台图标、部落字段、点击名字、屏蔽/举报、服务器聊天日志以及 Discord/聊天桥转发行为，都可能与真人消息不同。需要营造玩家聊天样式时，第一阶段应只做固定文案探针，用至少两名客户端把它与真人聊天逐项截图比对；完成实测前，只称“自定义名字聊天行”，不要宣称真实玩家身份或百分百真人样式。

## 服务器生成聊天与观察器兼容

在已核对的 AsaApi 2.03 源码中，默认 `MessagingManager::SendChatMessage_Impl` 会为单个接收者构造 `FPrimalChatMessage`，随后调用该接收者的 `ClientChatMessage`；`AddOnChatMessageCallback` 则由 AsaApi 对 `AShooterPlayerController::ServerSendChatMessage_Implementation` 的 Hook 调用。`AShooterGameMode::SendChatMessage(FPrimalChatMessage)` 又是独立的服务器广播入口。因此，“客户端已显示”“服务器已广播”“AsaApi 聊天观察回调已触发”是三种不同结果，不能互相代替；其他 AsaApi 版本必须重新核对对应源码。

官方 AsaApi 2.03 的默认 `MessagingManager::SendChatMessage_Impl` 会把每个接收者自己的 EOS ID 写入 `FPrimalChatMessage.UserId`。因此，“自定义发送者名 + 默认 `SendChatMessageToAll`”不能用于要求消息不绑定任何真人身份的虚拟角色。此类需求应优先使用官方 `MessagingManager` 扩展点，只覆写单接收者消息构造，显式初始化 `UserId`、`SenderIsAdmin`、平台和频道等字段；不要伪造随机 EOS ID。即便清空身份字段，也仍需双客户端验证点击名字、平台图标、屏蔽/举报、聊天历史和聊天桥行为。该结论是 2.03 源码事实，其他版本需重新核对对应 SDK。

反向 Hook `ClientChatMessage(FPrimalChatMessage)` 采集跨服、Discord 或机器人桥的客户端显示消息时，不要未经验证就把 `UserId` 当作发送者去重键。使用上述默认广播实现时，同一条消息在不同接收者上的 `UserId` 可能分别是各接收者 EOS；按它去重会把一条外部消息放大成“在线人数份”。优先使用桥明确提供的稳定发送者 ID；没有时使用规范化后的显示发送者名与正文组合，并用至少两名同服客户端验证同一条下行消息只采集一次。

AsaApi 2.03 的公开 `ICommands` 提供聊天回调的注册与移除，但没有“脱离玩家控制器主动发布一条 `AddOnChatMessageCallback` 事件”的通用接口。服务器生成的消息需要被其他插件消费时，应先确认并使用双方明确支持的互操作契约，例如目标插件公开 API、协议桥、共享外部入口，或双方都明确监听的服务器广播入口。没有契约时，应把“本服显示”“AsaApi 回调被观察”“第三方完成转发”作为三个独立验收结果；不要通过临时修改在线真人的姓名、平台 ID 或控制器状态来制造兼容性。

如果业务必须评估 synthetic controller / PlayerState 一类虚拟发送者，应把它视为高风险、版本相关的兼容实验，而不是通用默认方案：

- UObject 只在游戏线程通过引擎生命周期创建和销毁，跨 Tick 保存弱引用，并验证换图、重载和卸载清理；不要 `new` / `malloc` UObject，也不要手工伪造 `UNetConnection`。
- 登录、session、平台身份和玩家数据写入必须与基础对象创建分开验证。生成头 wrapper 能编译、字符串能解析或 getter 有返回，都不能证明 `NativeCall` ABI、对象布局和生命周期安全；先核对当前版本的精确签名，每轮只试一个对象、一个字段或 setter，记录调用前后与 getter 回读，异常后默认关闭并停止自动重试。
- 写玩家身份字段前，先确认目标观察器读取哪个 getter，以及读取发生在同步回调还是异步任务中。若只需一次同步读取，可评估限定目标 controller、线程和调用作用域的临时 getter 覆盖，让真人 controller、其他对象和作用域外调用全部走 original；这种做法仍需独立验证 Hook ABI，不能直接升级为默认身份实现。
- 调用玩家入站聊天链前，先审计命令检查、刷屏限制和同链路观察器。外部生成文本不得未经门禁直接进入聊天命令解析；优先拒绝配置中的命令前缀或使用明确的观察器入口。内部标记只有在所有目标插件、日志和跨服链都验证会安全处理时才能使用。
- 调用链中任何观察器若强制读取真实 `NetConnection`、Pawn、平台身份、玩家存档、权限或反作弊状态，半初始化虚拟对象都可能被跳过或导致异常。成功触发一个回调也不等于已经模拟真实平台登录玩家。
- 将观察器派发、本服显示和外部转发分别计数，失败分支只能执行一次显示出口，避免原始实现与显式广播重复。状态文案只能报告本插件确认的阶段；跨服、Discord 或机器人成功必须由目标端实收或明确 ACK 证明。
- 上服验收至少覆盖：一次输入只触发一次观察和一次显示、不会误执行聊天命令或刷屏限制、双客户端样式与历史、服务器日志、目标跨服/机器人/审计结果、玩家列表与人数统计、换图、重载和卸载。

这些规则是兼容性风险清单，不是要求所有插件采用同一种虚拟发送者实现；固定 Hook 组合、字段选择和业务回环策略应留在具体项目文档中。

发送外部生成的动态文本时，不要把该文本直接当作 `FString::Format` 的格式串。使用固定格式串（例如 `L"{}"`）传入动态文本，避免内容中的花括号触发格式解析异常。

接口名字和参数不能完全代表游戏内样式。发布前至少用目标服务器验证一次：聊天框前缀、发送者名、颜色、换行、历史记录、屏幕通知位置是否符合预期。

## 聊天命令注册与原消息拦截

- 普通聊天命令优先逐个使用 `AddChatCommand` 注册；不要默认用 `AddOnChatMessageCallback` 自行解析命令。ASA API 2.03 及以后会在 `Plugin_Unload()` 返回后按 DLL 模块自动清除命令和回调，因此不要再在 `Plugin_Unload()` 中手动调用 `RemoveChatCommand`、`RemoveConsoleCommand` 或 `RemoveRconCommand`。动态别名重载仍可使用对应 `Remove*`，但必须避开当前命令回调栈。
- AsaApi 会先检查正式聊天命令。首个 token 匹配后会执行命令回调、将 `command_executed` 标记为 `true`，并在进入游戏原始聊天广播前返回，因此不需要额外的“隐藏命令”参数。
- `AddOnChatMessageCallback` 返回 `true` 虽然也能阻止游戏默认广播，但所有聊天观察回调仍会被调用，而且自行识别的文本不会被标记为正式命令。聊天桥、Discord 转发或其他插件可能在看到 `command_executed=false` 时先记录或重新发送它，所以该接口更适合观察、过滤和修改普通聊天，不适合代替正式命令注册。
- 如果命令别名支持热重载，不要在当前聊天命令回调栈内立即 `RemoveChatCommand` / `AddChatCommand`。AsaApi 的命令检查会直接遍历命令容器，回调内修改可能让迭代器失效；应延迟到下一 tick/timer 再同步别名。控制台/RCON 重载也可以统一走相同的延迟同步路径。
- 改成正式命令后若仍只有发送者自己看见，先让第二名玩家确认是否真的收到，排除客户端本地回显；若其他玩家也能看到，再排查是否有其他聊天插件忽略 `command_executed` 并主动重发。

## 安全性

如果消息从聊天命令回调里发出，可以按项目情况选择同步发送或延迟发送。若遇到对象生命周期、回调重入或兼容问题，再评估延迟一 tick 或一秒，并保存玩家弱引用。延迟发送是兼容策略，不是所有插件都需要采用的默认写法。

## 配置建议

玩家可见文字通常建议配置化，便于不同服务器调整语气和语言。颜色是否配置化取决于插件定位：如果颜色是服主会主动调整的样式，提供配置；如果只是固定状态语义，可以用代码默认值并在文档说明。

玩家提示、配置说明和面向服主的日志应采用服务器实际使用的业务词汇，而不是直接翻译底层接口名。例如 ArkShop API 的函数名是 `GetPoints` / `SpendPoints`，但服务器对外称为“金币”时，文案应统一写“花费 N 金币”“金币不足”“退还 N 金币”，不能显示“消耗 N 点”。代码标识无需为了文案改名。

固定且不会歧义的物品名称保持简洁。优先显示“钻头”“背包”，不要默认附加“（采集器）”“（鞍袋）”等同义括号；只有多个物品主名称相近、确实需要帮助玩家区分时才追加别名。

颜色配置推荐用 `[R, G, B, A]`，范围 `0.0..1.0`，读取时 clamp。文本模板可以支持简单命名占位符，未知占位符保留原样。
